# Журнал архитектурных решений

Этот файл фиксирует решения, их причины и последствия. Он не является списком всех предложений из переписок: предложение считается решением только после явного выбора владельца или фактического утверждения изменения в Git.

## D-001. Использовать статический сайт на Hugo

**Дата:** до 2026-10-30; подтверждено миграцией в Git  
**Статус:** принято

Сайт строится на Hugo и публикуется через Cloudflare Pages. Текущая архитектура не требует серверной CMS, регистрации читателей или базы данных.

**Причина:** архив преимущественно состоит из заранее подготовленных публикаций; статическая генерация уменьшает сложность эксплуатации и поверхность атаки.

**Последствие:** исходные Markdown-файлы и Hugo layouts — основные компоненты сайта. Новые серверные сервисы не добавлять без конкретной необходимости.

Подтверждающий коммит миграции: 9e4cc6f299b37302db62dccd07de984eb1e1db8c.

## D-002. Использовать Cloudflare Pages для сборки и публикации

**Дата:** 2026-10-30  
**Статус:** принято

GitHub хранит исходники, Cloudflare Pages собирает Hugo и публикует production-версию. Для Pull Request используются Preview Deployments.

**Причина:** Cloudflare уже выполняет сборку и публикацию. Повторный workflow GitHub Actions, который делает то же самое, создавал бы дублирующую инфраструктуру.

**Последствие:** не добавлять GitHub Actions для повторной Hugo-сборки/публикации без отдельного решения. Проверки качества контента и безопасности можно рассматривать отдельно.

Подтверждающий коммит настройки Cloudflare Pages: c47133d05f32a41c74ea892b53982355933ce10d.

## D-003. Не изменять main напрямую; использовать ветки и Pull Requests

**Дата:** 2026-10-31 и далее  
**Статус:** принято как рабочий процесс

Изменения подготавливаются в отдельных ветках и проверяются через PR. Слияние остаётся отдельным решением владельца.

**Причина:** возможность сравнить изменения, проверить Preview и откатить отдельный этап.

**Последствие:** не писать в main и не сливать PR без явного разрешения.

## D-004. Первоначально сохранить и усилить импортёр LiveJournal

**Дата:** 2026-10-31  
**Статус:** superseded / заменено более поздним решением

Первоначально владелец выбрал умеренную переработку с сохранением Hugo, Python-импортёра LiveJournal и Gemini. PR №1 добавил санитизацию HTML, проверку метаданных Gemini, безопасную сериализацию YAML, ограничения сетевых запросов и изображений, тесты и workflow.

**Причина первоначального решения:** сохранить текущую автоматическую публикацию, но укрепить безопасность.

**Последствие:** создан PR №1 security/moderate-hardening. Он остался Draft и не был слит в main.

Позднее владелец выбрал отказ от импортёра. Поэтому D-004 больше не описывает целевую архитектуру. Код PR №1 не следует сливать как готовое решение.

## D-006. Сохранить архивные публикации и изображения при удалении импортёра

**Дата:** 2026-11-05  
**Статус:** принято; проверено в PR №3

Перед удалением импортёра проверено, что публикации и локальные изображения уже находятся в Git. В PR №3 не меняются content/posts/, data/posts/, data/images/ и static/images/.

**Подтверждённое состояние на main f7b3e8e:**
- 147 файлов content/posts/;
- 143 файла data/posts/;
- 4 файла data/images/;
- 4 файла static/images/;
- Git blob SHA каждой пары локальных изображений совпадает.

**Ограничение:** data/posts/ содержит на четыре файла меньше, чем content/posts/, поэтому это не полное резервное зеркало публикаций. Одно внешнее изображение в комментарии также не локализовано.

**Последствие:** архивные каталоги сохраняются. Удаление импортёра не должно затрагивать существующий контент.

## D-008. Не менять пользовательский дизайн в рамках удаления импортёра

**Дата:** 2026-11-05  
**Статус:** принято для PR №3

PR №3 удаляет только старую автоматизацию и скрипт. Hugo templates, CSS, шрифты, навигация и тексты публикаций не меняются.

**Причина:** этап посвящён отключению старого импортёра, а не редизайну.

**Последствие:** вопросы внешнего Tailwind CDN, Google Fonts, структуры шаблонов и пользовательского интерфейса рассматриваются отдельно.

## D-009. Не отключать Goldmark unsafe и не включать строгую CSP без инвентаризации

**Дата:** 2026-11-06  
**Статус:** принято как ограничение безопасности до отдельного решения

В config.toml включён markup.goldmark.renderer.unsafe = true. В публикациях встречаются HTML-вставки и iframe, а шаблон поиска содержит inline JavaScript. Общий шаблон использует внешний Tailwind CDN и Google Fonts.

**Причина:** без проверки можно сломать исторические медиа-вставки, форматирование и поиск либо заблокировать необходимые ресурсы.

**Последствие:** сначала инвентаризировать HTML, iframe, inline-скрипты/стили и внешние домены; затем разработать политику безопасности и проверять её на Preview.

## D-010. Не предоставлять внешнему редактору доступ к репозиторию на текущем этапе

**Дата:** 2026-11-05  
**Статус:** отложено

Обсуждались три модели: PR с ограничением через review/CODEOWNERS, отдельный репозиторий контента и передача TXT владельцу для обработки.

**Решение:** настройку доступа редактора пока отложить.

**Последствие:** не добавлять collaborators, CODEOWNERS, CMS или отдельный content repository без нового запроса.

## D-011. Документировать проект внутри репозитория

**Дата:** 2026-11-06  
**Статус:** принято

В корне репозитория используется AGENTS.md, а в docs/project/ — PROJECT_STATUS.md, ARCHITECTURE.md, DECISIONS.md и HANDOFF.md.

**Причина:** обеспечить переносимость контекста между чатами, IDE и агентами, не полагаясь на историю диалогов.

**Последствие:** поддерживать документы инкрементально, отделять проверенные факты от предположений и обновлять только затронутые файлы.
