# Инструкции для AI-агентов и разработчиков

## Назначение проекта

Edelstein Archive — статический архив публикаций протоиерея Георгия Эдельштейна. Основной сайт собирается Hugo и публикуется через Cloudflare Pages из GitHub.

Приоритеты проекта:

1. Сохранность и точность архивных текстов.
2. Предсказуемая и безопасная публикация.
3. Минимальная сложность инфраструктуры.
4. Удобство чтения и поиска без ненужной серверной функциональности.

## Источники истины

При расхождениях используй следующий порядок:

1. Текущее содержимое Git-репозитория и его история.
2. docs/project/PROJECT_STATUS.md — подтверждённый снимок состояния на указанную дату.
3. docs/project/ARCHITECTURE.md — описание структуры и зависимостей.
4. docs/project/DECISIONS.md — принятые решения и их причины.
5. docs/project/HANDOFF.md — оперативная передача работы; она может устареть.

История чатов объясняет намерения и причины, но сама по себе не доказывает, что изменение попало в репозиторий. Всегда проверяй GitHub перед продолжением старой задачи.

## Правила работы

- Перед началом прочитай этот файл, docs/project/PROJECT_STATUS.md и docs/project/HANDOFF.md.
- Изучи только файлы, необходимые для текущей задачи, и их непосредственные зависимости. Не проводи полный аудит репозитория для небольшого локального изменения.
- Проверь текущую ветку, HEAD и незакоммиченные изменения до любой записи.
- Не вноси изменения непосредственно в main. Используй отдельную ветку и Pull Request.
- Не сливай PR, не закрывай существующие PR и не меняй настройки GitHub/Cloudflare без явного разрешения.
- Не утверждай, что тест, сборка, preview или публикация прошли, если результат не был фактически проверен.
- Не запускай старые workflow синхронизации LiveJournal. Их удаление находится в PR №3; до слияния PR старый workflow остаётся в main.
- Не возвращай в проект fetch_new_posts.py, .github/workflows/sync_posts.yml или автоматическую синхронизацию LiveJournal без нового явного решения владельца.

## Сохранность архивного содержания

- Не исправляй орфографию, пунктуацию, формулировки, даты или метаданные публикаций молча.
- Различай оригинальный текст, исправление переноса, редакторскую правку и форматирование.
- Не перезаписывай и не удаляй публикации, комментарии, изображения или резервные копии без явного задания.
- content/posts/ — действующий источник публикаций Hugo.
- data/posts/, data/images/ и static/images/ — архивные данные; сохраняй их, пока не принято отдельное решение.
- data/posts/ не является полным зеркалом content/posts/: на момент последней проверки файлов было 143 и 147 соответственно.
- Не редактируй public/ вручную. Это сгенерированный HTML, который сейчас также присутствует в Git; его актуальность требует отдельной проверки.
- Внешние iframe, изображения и ссылки в старых публикациях могут быть частью архивного материала. Не удаляй их массово и не отключай HTML-рендеринг без инвентаризации и проверки результата.

## Архитектурные ограничения

- Сохраняй статическую архитектуру Hugo + GitHub + Cloudflare Pages, если задача явно не требует её изменения.
- Не добавляй CMS, базу данных, серверную часть, новые сервисы или зависимости без обоснования.
- Не добавляй GitHub Actions для повторной сборки и публикации Hugo без отдельного решения: Cloudflare Pages уже выполняет сборку и создаёт Preview Deployments для PR.
- Дополнительные проверки качества можно рассматривать отдельно от повторной сборки/публикации.
- Не меняй пользовательский дизайн, шаблоны, CSS, шрифты и навигацию в рамках задач безопасности или документации, если это прямо не запрошено.

## Безопасность

- Считай архивный HTML недоверенным до проверки. В config.toml сейчас включён markup.goldmark.renderer.unsafe = true; это связано с исторической HTML-разметкой и iframe-вставками.
- Не переключай unsafe на false и не вводи строгую CSP вслепую: сначала проверь существующие публикации, iframe, inline JavaScript/CSS и внешние ресурсы.
- Не добавляй секреты, токены или ключи в Git. Секреты GitHub доступны только через настройки GitHub; не пытайся выводить их значения.
- Не считай успешную сборку Hugo полноценным аудитом безопасности или качества контента.
- Проверяй, что внешние ссылки и ресурсы действительно нужны; не удаляй архивные ссылки без согласования.

## Проверки и завершение задачи

Подбирай проверки по масштабу изменения:

- Для контента: корректность Front Matter, ссылки, изображения и отсутствие непреднамеренного изменения текста.
- Для Hugo: сборка проекта, если доступен Hugo и конфигурация сборки; иначе честно укажи, что локальная сборка не выполнялась.
- Для шаблонов/безопасности: проверь вызываемые шаблоны, внешние ресурсы и соответствующие страницы Preview.
- Для удаления: проверь все ссылки и зависимости до удаления, а после — diff и сборку.

В конце работы укажи:
- что изменено и в какой ветке;
- commit SHA или PR;
- какие проверки действительно выполнены и их результаты;
- что не проверено;
- какие решения или действия остались за владельцем.

## Документация

Поддерживай документы в docs/project/:

- PROJECT_STATUS.md — текущее подтверждённое состояние;
- ARCHITECTURE.md — структура и связи компонентов;
- DECISIONS.md — решения и причины;
- HANDOFF.md — текущая точка продолжения.

Обновляй только документы, которых коснулось изменение. Не копируй исходный код в документацию и не дублируй одну и ту же информацию в нескольких файлах. Не записывай предположения как факты; явно помечай неизвестное и непроверенное.
